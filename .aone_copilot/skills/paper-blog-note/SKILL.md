## 使用场景

当用户要求把一篇论文（不包括综述）、技术报告或 arXiv 链接整理到当前项目的静态笔记博客时，使用本 skill。

当前博客是 `index.html` 单文件静态站点，笔记数据维护在页面脚本中的 `NOTES` 数组里，图片资源放在 `assets/` 下。

## 工作流程

1. **收集论文信息**
   - 优先读取论文 HTML/abstract 页面和 PDF。
   - 记录标题、作者、机构、会议/年份、arXiv 链接、代码链接。
   - 如果 PDF 文本提取失败，可改用 arXiv HTML 页面、abstract 页面或可访问的源码页面。

2. **理解论文结构**
   - 至少覆盖：Abstract、Introduction、Method、Data/Benchmark、Experiments、Ablation、Conclusion。
   - 不只摘抄摘要；需要提炼问题背景、核心方法、实验设置（如果文章介绍了所需硬件资源，需要进行整理）、实验结果和结论、局限与个人启发。
   - 对关键数字保持准确，例如 win rate、FPS、benchmark 名称、数据规模、窗口长度等。

3. **保留关键图片**
   - 下载论文中对理解最关键的图到 `assets/papers/<paper-slug>/`。
   - 优先保留：方法总览图、训练/推理结构图、数据流程图、核心实验/效率图、稳定性或消融图。
   - 正文中用 `<figure class="figure">` 引用，并写清晰中文图注。
   - 检查已下载图片是否都被引用；避免下载了关键图但正文遗漏。

4. **写入博客笔记**
   - 在 `index.html` 的 `NOTES` 数组中新增或更新一条 note。
   - 字段包含：`id`、`title`、`category`、`date`、`readTime`、`tags`、`summary`、`content`。
   - `category` 应优先复用现有目录分类；不要因为是论文笔记就默认创建 `论文阅读`。如果需要创建新的分类，必须先询问用户意见。
   - `tags` 应覆盖模型类型、任务、关键技术和 benchmark。

## 推荐笔记结构

使用以下结构组织 `content`：

```markdown
## 一句话总结
用 1 段话讲清论文核心贡献和为什么重要。

## 论文信息
- 标题
- 作者/机构
- 会议或版本
- 链接

## 背景：为什么这个问题重要？
说明现有方法痛点和论文要解决的核心问题。

## 方法：核心设计
按 2-4 个小节拆解关键方法，解释“为什么这样设计”。

## 数据与评测
说明训练数据、评测集、评测方式和任务设置。

## 实验结果
保留关键表格或数字，解释这些结果意味着什么。

## Ablation：哪些设计最关键？
总结消融实验和设计因果关系。

## 我的理解与启发
结合工程或产品视角讲清可借鉴点。

## 局限与待观察点
指出数据、评测、部署、泛化或成本方面的问题。

## 结论
用 1 段话收束论文价值。
```

## 写作风格

- 使用中文，风格清晰、结构化、可复习。
- 先给结论，再展开细节。
- 避免堆砌论文原文；重点写“我理解的贡献、取舍和启发”。
- 对方法部分要解释机制，而不是只列名词。
- 表格可用 HTML table，图片用现有 `.figure` 样式。
- 标题层级使用 `##` / `###`，不要使用一级标题。

## 质量检查

完成后必须检查：

- `index.html` 内容完整，无开发残留标记。
- 所有下载的论文图片都能被页面引用，或删除未使用图片。
- `read_lints` 对 `index.html` 无错误。
- 抽取脚本后用 `node --check` 检查 JS 语法。
- `git diff --check` 通过。
